# M15 验收单 · 主线程重算开销基线 + 灾难级回归门

> 依据：M14 验收单 §五 第 5 项 / M11 引入的性能回退（`nyquistFull` 0.06 ms → 2.4 ms）无人量化——
> 本项目此前只有**正确性**门（parity / audit / uidata），没有**开销**门。
> 本里程碑建立主线程重算开销基线，并把它接入 CI。交付 = 可运行版本 + 本验收单。版本 **2.10.0**。
> **注意：本里程碑不改动任何应用代码**（仅新增脚本/文档 + 版本号），因此无需浏览器复验。

## 一、交付范围

| 项 | 内容 |
|---|---|
| 新巡检脚本 | `v2/scripts/perf.mjs`：对「工具页参数变化时**主线程同步执行**的内核调用」逐个计时（57 项，30 次平均，含 JIT 预热），打印降序表 + 主线程合计 |
| 新命令 | `npm run perf` |
| 断言策略 | **只拦灾难级回归**：单项 ≤ **25 ms**、主线程合计 ≤ **150 ms**（基线最大项 ≈ 3.8 ms，留 ~6× 余量，避免慢机器误红）；单项 ≥ **5 ms** 打印 ⚠ 供人工复核 |
| worker 标注 | `pid · pidOptimize`（≈ 3.7 ms）在工具内走 **worker**，表中标注〔worker〕且**不参与**主线程预算断言 |
| CI | `.github/workflows/ci.yml` 的 `v2` 作业新增步骤「主线程重算开销巡检（灾难级预算 · M15）」 |

## 三、结论

- [x] **无 ≥5 ms 的主线程项**（⚠ 项 0 个）：最重的三项都在 1–4 ms，远低于一帧 16.7 ms 的预算。
- [x] 「系统分析」页最重的参数变化路径（奈奎斯特视图）≈ **2.4 ms**：即 M11/M14 的围线加密成本，
      仍然安全；且经 `useMemo` 记忆，仅在参数变化时重算。
- [x] 计算量最大的 `pidOptimize` 在主线程之外（worker）→ **不造成输入卡顿**。
- [x] `parseDataSeq(2000 行)` 属**一次性**操作（粘贴触发），不在逐帧路径上。
- [x] 门非空转：把 `BUDGET_ITEM` 临时改成 1 ms → `npm run perf` 立即以退出码 1 报出 5 个超预算项（含具体 ms 值），随后还原 → 16.3 ms 全绿。

## 五、说明与遗留

1. **责任边界**：本脚本只覆盖 `src/core` 的**内核调用**开销（主线程卡顿的主要来源）；
   JSX 渲染、图表绘制、DOM 交互仍由里程碑的**浏览器走查**负责（CI 不跑浏览器）。
2. **门的敏感度是有意放宽的**：25 ms / 150 ms 只能拦数量级退化；M11 那次 38× 退化（0.06→2.4 ms）
   **不会**触发本门——因此每次内核改动后仍应把 `npm run perf` 的输出与 §二 基线表**人工比对**。
   若将来要收紧，正确做法是引入「记录基线 + 相对阈值 + 小项忽略下限」，而不是把阈值压到基线附近（会抖）。
3. `sincReconstruct`（3.8 ms）与 `rootLocus`（1.8 ms）是当前最值得优化的两项，但**本轮未动**：
   它们都在 parity 的数值一致性保护下（优化需保持 v1↔v2 逐字段一致），收益（<4 ms）与风险不成比例。
4. 测量含 JIT 预热与 30 次平均；跨机器绝对值会变，故门较宽——同一机器上的**相对变化**才是有效信号。
5. 其余已知边界见《M12 验收单》§五（实例回读需跨 13 工具）与《M14 验收单》§五（采样常量调参须知）。
